### 2. 根因

1. **防篡改锁成了死锁**：`settleNative` 用 prior-wins 锁住 `age / appearance / body / 三围` 是为了防止大模型在长对话中记忆漂移乱改人设，但没有给玩家留出**脚本独占的纠错操作通道**，导致一旦首次建档写歪，玩家连用括号指令让 AI 改都改不动。
2. **生成端缺少「脚本兜底律」**：新人物入库（`newCharacter`）与一句话补人（`expandContact`）完全依赖模型自觉挑年龄；模型要么写 `<18` 在旧版被删字段回落成骨架 `25`，要么对「大一新生/实习生」随手填个默认 `25`，而脚本既未解析中文数字年龄，也未按职业/身份关键词做确定性年龄区间收敛。
3. **已发行旧存档的存量错位**：旧存档里已经落库为 `age: 25, occupation: "高二学生"` 的人物，即便修好 `newCharacter`，也会被 `settleNative` 第 69 行继续死锁在 `25`。

##### B. 优先级规则（「玩家显式写了年龄就以玩家为准」vs「模型随机填年龄」）

1. **数字提取与中文数字解析（`parseExplicitAge`）**：
   - 先从玩家显式输入文本（`briefText`，如开局一句话描述「19岁清冷美院学妹」或玩家在弹窗里手填的数字）中提取显式年龄：匹配 `/(?:^|[^\d])([1-9]\d)\s*(?:岁|周岁)/` 或纯数字输入，并支持中文年龄词（`十八岁→18`、`十九岁→19`、`二十岁→20` … `三十五岁→35`）。
   - 任何显式提取到的年龄先按 `[18, 80]` 钳位（例如玩家写「17岁高二女儿」，显式年龄被硬钳为 `18`）。
2. **最高优先级：玩家显式操作或显式文本（Player Explicit Wins）**：
   - **场景 1（玩家在纠错弹窗 `PLAYER_EDIT_CHARACTER` 或开局表单 `save-contact` 手动保存）**：100% 以玩家填的 `age`（`18–80`）和 `occupation` 为准，**脚本绝不覆盖玩家手填值**。
   - **场景 2（开局一句话补人 `expandContact(brief)`）**：若 `brief` 中包含玩家写的显式年龄（如「26岁留级博士」或「28岁年轻小姨」），钳位到 `[18, 80]` 后直接采用玩家写的年龄，**跳过职业区间覆盖**；仅当玩家在 `brief` 里没写年龄时，才对模型返回的 `parsed.age` 执行职业区间收敛。
3. **次优先级：模型首次建档/生成时的矛盾纠正（管不管「职业与年龄同时出现矛盾」的人？）**

const CN_DIGITS = { 零: 0, 一: 1, 二: 2, 两: 2, 三: 3, 四: 4, 五: 5, 六: 6, 七: 7, 八: 8, 九: 9 };
export function parseExplicitAge(input) {
  if (typeof input === 'number' && Number.isFinite(input)) return Math.round(input);
  const s = String(input ?? '').trim();
  if (!s) return null;
  if (/^-?\d+(?:\.\d+)?$/.test(s)) return Math.round(Number(s));
  const arab = s.match(/(?:^|[^\d])([1-9]\d)\s*(?:岁|周岁)/);
  if (arab) return Number(arab[1]);
  const cn = s.match(/([一二三四五六七八九]?十[一二三四五六七八九]?|[一二两三四五六七八九])\s*(?:岁|周岁)/);
  if (cn) {
    const token = cn[1];
    if (token === '十') return 10;
    if (token.startsWith('十')) return 10 + (CN_DIGITS[token[1]] || 0);
    if (token.endsWith('十')) return (CN_DIGITS[token[0]] || 1) * 10;
    const [tens, ones] = token.split('十');
    if (ones !== undefined) return (CN_DIGITS[tens] || 1) * 10 + (CN_DIGITS[ones] || 0);
    return CN_DIGITS[token] ?? null;
  }
  return null;
}

export function matchAgeBand(c) {
  const occ = String(c?.occupation || '').trim();
  const rel = String(c?.relationshipLabel || '').trim();
  const primary = `${occ} ${rel}`;
  for (const rule of AGE_BAND_RULES) {
    const target = rule.relOnly ? rel : primary;
    if (rule.re.test(target)) return rule;
  }
  const fallback = `${c?.knownFacts || ''} ${c?.firstContactEvidence || ''}`;
  for (const rule of AGE_BAND_RULES) {
    if (!rule.relOnly && rule.re.test(fallback)) return rule;
  }
  return null;
}

export function reconcileCharacterAge(raw, { briefText = '', skeletonDefault = 25 } = {}) {
  const clamp = (n) => Math.min(80, Math.max(18, Math.round(n)));
  // 1. 玩家在一句话描述里显式写了年龄 → 钳到 [18, 80] 后直接以玩家为准
  const explicitFromBrief = briefText ? parseExplicitAge(briefText) : null;
  if (explicitFromBrief !== null) return clamp(explicitFromBrief);

  const parsedRaw = parseExplicitAge(raw?.age);
  const band = matchAgeBand(raw);
  if (!band) {
    return parsedRaw !== null ? clamp(parsedRaw) : skeletonDefault;
  }
  if (parsedRaw === null) return band.defaultAge;
  const clamped = clamp(parsedRaw);
  // 模型/旧骨架随手塞了 25 岁，且 25 岁不在该职业区间内 → 直接落到该职业默认典型年龄
  if (clamped === skeletonDefault && (clamped < band.min || clamped > band.max)) {
    return band.defaultAge;
  }
  if (clamped < band.min) return band.min;
  if (clamped > band.max) return band.max;
  return clamped;
}

### 8. 风险与「本轮不做」（问题 A）

### 2. 根因

1. **交互断层**：`w53` 是全池唯一一张**「需要玩家提供开放式命题（愿望内容）」**的券（其余 52 张券如「便利店十分钟」「海景房一晚」「私人海岛包岛三日」自带完整剧本，玩家只需选跟谁去）。拿通用模板套 `w53`，导致玩家没有输入愿望的专属入口。
2. **提示词自摆乌龙**：`buildItemInputDraft` 把 `w53.hint`（「终端屏幕整个黑了，只剩一行字在闪：说吧，你想要什么。」）原样塞进用户发送框；大模型看到用户消息里写着「说吧，你想要什么」，最顺理成章的续写就是让终端停在这句台词上等玩家下一轮回答——而下一轮 `pendingUndo` 已经被 `settleEvents` 清零，模型再也不知道有过这张券。
3. **缺少「脚本+协议双轨兑现通道」**：玩家许愿「给我一栋汤臣一品顶层豪宅」或「给我一套湾流私人飞机」，如果只靠模型写正文而脚本不落资产、或者模型忘了发 `ASSET_GRANT`，玩家看财富页依然是空的；反过来如果允许脚本直接印 100 亿现金，又会击穿 `assertEconomy` 或毁掉神豪提现核心循环。

### 3. 设计（含取舍与被否掉的备选）

#### 3.1 总体架构回答：其它 52 张券要不要一起收口？还是只给 `w53` 单开一条路？

- **明确结论：53 张玩法券共享同一套「待兑现投放 + 撤销窗口」底层管道，但在入口与结算上分为两档——`w01–w52` 保持「预设体验券（零额外必填项 + 可选补充心愿备注）」，`w53`（rainbow 终极大奖）单开「终极许愿专属契约（四维许愿方向 + 必填愿望文本 + 脚本确定性预兑现 + 强制当轮完结注入）」**。
- **为什么不给 `w01–w52` 强加必填许愿框**：
  - `w01–w52`（见 `wheel-pool.js`）本身已经把「获得什么、在哪、跟谁」写得清清楚楚（如 `w18` 私密试衣间独享、`w43` 一日女友、`w52` 后宫出海一周）。如果强迫玩家每次用普通券都填愿望表单，会把高频轻快的用券体验变成填表负担。
  - **但 `w01–w52` 顺手享有一项收口升级**：在普通玩法券的 `prizeUseNowForm` 中，若玩家在 `#pzn_draft` 引导词里自己补充了定制细节，或 `w53` 填写了专属愿望，统一写入 `inventoryItem.wishText`（可选新字段，默认 `''`），并由 `projection(s)` 的 `mustDepictUsedItems` 带上 `playerWish` 字段喂给模型——这样玩家用 `w31 全城大屏一小时` 时自己补了一句「大屏上放向苏晚表白的烟花字」，模型在 `_context.mustDepictUsedItems` 里也能读到！
- **为什么 `w53` 禁止「排入日程」、只走「立即许愿兑现」**：
  - 排入日程（`prizeScheduleForm`）是给「某月某日某时去某地赴约（如早茶包桌、海岛七日）」用的；「向终端许一个终极愿望」是瞬发特权，排进日历只会制造一条没有许愿文本的死日程。因此背包里 `it.refId === 'w53'` 时，只渲染主按钮 **「✦ 立即许愿」**（不渲染「排入日程」按钮；引擎侧若收到 `w53` 的非 immediate 请求也友好兜底或要求 `wishText`）。

#### 3.3 为什么不设「脚本直接发百亿现金」通道？（经济边界与 `assertEconomy` 衔接）

1. **核心乐趣保护**：《神豪终端》的核心循环是「为女人花钱 / 破防互动 → 进原始奖池 → 乘神豪倍率（10x/8x/5x/3x/2x）提现暴富」。如果 `w53` 允许脚本直接 `cashCents += 100亿`，玩家一发入魂直接毕业到 `财阀霸主·二倍`，所有女性奖池与提现倍率体系当场报废。
2. **如果玩家在自由心愿里写「我要 10 个亿现金」怎么处理？**
   - 这正好进入 **「愿望降级与转化口径」**（见 §3.4）：任何直接索要巨额银行余额/凭空印钞的愿望，统一转化为**「终端为你全额免款交割等值顶奢旗舰不动产/核心集团股权（走 `ASSET` 顶奢旗舰档入账，不污染 `cashCents` 与提现倍率基数 `tierBasis`）＋ 当轮与在场女性的顶级排面暴击事件（产出高额待提现奖池）」**。
3. **与 `assertEconomy`（`engine.js:1252-1269`）的严密咬合**：
   - `assertEconomy` 第 1255 行硬校验：`s.user.cashCents === add(s.user.initialCashCents, add(t.income, -t.expense))`。
   - 本方案中，`w53` 选 `ASSET` 通道时，脚本写入 `s.finance.assets[assetId]`（`bookValueCents: ASSET_TIER_TABLE[kind].TOP, basisCents: 0, acquisitionIsInitial: true`）并写入 `addLedger(..., { kind: 'ASSET_GRANT', direction: 'NONE', amountCents: 0 })`：
     - 对 `t.income` 与 `t.expense` 贡献均为 `0`，`LEDGER_MISMATCH` **永远为 0 风险**；
     - 因 `acquisitionIsInitial: true` 且 `basisCents: 0`，`tierBasis(s)`（`engine.js:1162-1168`）不会把这件白得的顶奢资产算进「后购资产成本」，**绝不稀释玩家现有的 10 倍/8 倍神豪提现倍率**；
     - 资产估值直接取 `ASSET_TIER_TABLE[kind].TOP`（与 `ASSET_VALUATION_BOUNDS` 完全兼容），且 `isCustom: false`，玩家甚至可以拿这件愿望赐予的顶奢资产去暗夜赌场上桌或转赠给女性！
4. **与撤销窗口（`PLAYER_UNDO_ITEM_USE`）及 `mustDepictUsedItems` 生命周期的严密咬合**：
   - **当玩家在正文生成前点击「撤销使用」**：
     - `item.undoSnapshot` 中完整保存了本次 `w53` 的脚本副作用快照：
       - 若 `wishKind === 'ASSET'`：`undoSnapshot = { grantedAssetId: assetId, grantedLedgerId: op.operationId + ':wish_asset' }`；撤销时从 `s.finance.assets` 删除 `grantedAssetId`、从 `s.finance.ledger` 删除 `grantedLedgerId`。
       - 若 `wishKind === 'ROMANCE'` 且改动了 `presentCharacterIds` 或 `arousal`：`undoSnapshot = { priorPresentIds: [...], targetId, priorArousal }`；撤销时原样还原 `s.scene.presentCharacterIds` 与 `c.arousal`。
     - 同时清空 `item.wishKind = null`、`item.wishText = null`，并由 `removeDraftBlock` 精确剔除聊天输入框里的 `【终极许愿：…】` 引导词。
   - **`mustDepictUsedItems` 与 `activeWish` 的生命周期**：
     - 只要 `item.pendingUndo === true`，`projection(s)` 不仅在 `mustDepictUsedItems` 里输出该项，而且针对 `refId === 'w53'` 在 `_context` 顶层额外挂载高优先级对象 **`activeTerminalWish`**（见 §5）。
     - 当下一轮正文生成完毕、`settleEvents`（`engine.js:1532`）执行时，`item.pendingUndo` 被置为 `false`，`activeTerminalWish` 在再下一轮自动退场，零残留 token。

#### 3.4 强制当轮兑现注入 & 愿望超纲/冲突时的确定性降级口径

为了彻底杜绝模型再写出「终端屏幕黑了，问你想要什么」然后戛然而止，我们在**三个层面**同时锁死：

1. **聊天输入框引导词（`buildWishInputDraft`）彻底废除发问句 `hint`**：
   - 旧版把 `hint`（「说吧，你想要什么。」）拼在末尾，等于诱导模型停在发问。
   - 新版 `w53` 专用引导词改成**「玩家已经对着黑屏说出了愿望，终端当场锁定并已启动现实兑现」**的完成态指令（定稿见 §6.3）。
2. **`_context.activeTerminalWish` 顶层强制待办索引**：
   - 在 `projection(s)` 顶层输出 `activeTerminalWish`，内含 `wishKind`、`wishText`、`targetNames`、`preGrantedAsset`（若脚本已自动入账资产）及硬性 `directive`。
3. **四档确定性降级口径（写进 `protocol.txt` 第 18 行 `16.1`，严禁模型“看情况”或拒绝兑现）**：
   - **口径 ①（禁止停在发问/禁止拖延到下一轮）**：玩家的愿望已在 `activeTerminalWish.wishText` 中明确给出。本轮正文只能用 **1 句以内**写终端黑屏金字一闪而过的确认仪式，随后**必须在本轮正文内把愿望落地成已经发生的现实结果与人物反应**，严禁停在「终端问你想要什么」「等待明天交割」或「正在筹备中」。

### 6. 旧存档兼容（问题 B）

1. **未使用的旧存档 `w53` 券**：旧存档 `inventory` 中的 `w53` 条目没有 `wishKind` 与 `wishText` 字段，经 `schemas.state.parse` 时由 `.default(null)` 自动补为 `null`；玩家在旧存档里点开背包，直接看到升级后的「✦ 立即许愿」按钮与四方向许愿台。
2. **旧存档里已经用掉、变成 `status: 'USED', pendingUndo: false` 却没兑现的 `w53` 券怎么办？**
   - 玩家反馈中提到的现场正是：「抽到了 rainbow 的终端最终愿望，已经点过使用，正文只写到『说吧，你想要什么』就结束了，券已经变成『已核销』」。
   - **旧存档自愈补救（写进 `sanitizeInventoryAndUnlocks(s)`）**：
     - 检查 `s.inventory` 中是否存在 `item.refId === 'w53' && item.status === 'USED' && item.pendingUndo === false && !item.wishText && !s.facts?.['legacy_w53_restored:' + item.itemId]`。
     - 因为新版通过 `w53` 许愿一定会留下非空的 `item.wishText`，所以 **`status === 'USED'` 且 `!item.wishText` 的 `w53` 100% 是在旧版没填愿望就被空放浪费掉的冤案券！**
     - `sanitizeInventoryAndUnlocks(s)` 发现这类空放的旧版 `w53` 时，**自动将其状态恢复为 `status: 'READY', usedDate: null, usedRevision: null`**，并记入幂等锁 `s.facts['legacy_w53_restored:' + item.itemId] = { type: 'LEGACY_W53_RESTORE', itemId: item.itemId }`，置 `out.changed = true`！
     - **玩家体验**：之前被吞掉愿望的老玩家更新后一打开背包，发现那张被白白浪费的虹阶「终端最终愿望」**已经重新回到「待使用」列表**，可以立刻点「✦ 立即许愿」真正兑现一次！
